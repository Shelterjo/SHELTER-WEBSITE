# ROLLBACK — التراجع إلى آخر إصدار مستقر

| البند | القيمة |
|---|---|
| **الغرض** | إذا سبب إصدار مشكلة نعود بسرعة إلى **Previous Stable Release**: الكود، والإعدادات، والـMigrations بأمان، والمحتوى، والـCache، والتحويلات. **لا تُعتبر معمارية النشر مكتملة بدون خطة تراجع** (M35 §3) |
| **الحالة** | `SPEC — READY FOR BUILD` · التنفيذ: `NOT STARTED` |
| **مرحلة البناء (M36 §6)** | **PHASE 7** (production release process). تراجع المحتوى من **PHASE 1** (`content_versions`). خطة المشروع: P08 · P11 |
| **المتطلبات** | M35 §3 · §46 · §58 · DEPLOY-009 · DEPLOY-013 · DEPLOY-014 · OPS-023 · OPS-024 · AC-5 · G14-TF-08 · FINAL-ARCHITECTURE-REVIEW §13 (التراجع) |
| **المراجع الملزمة** | [`DEPLOYMENT`](DEPLOYMENT.md) · [`CACHE-CDN`](CACHE-CDN.md) · [`DISASTER-RECOVERY`](DISASTER-RECOVERY.md) · [`PLATFORM-ARCHITECTURE`](../architecture/PLATFORM-ARCHITECTURE.md) |

## 1. ماذا يُرجَع وكيف
| الطبقة | الطريقة | الزمن المستهدف |
|---|---|---|
| **أسرع رافعة: الأعلام** | Safe Mode، أو تعطيل ميزة أو تجربة أو تكامل اختياري من `feature_flags` (OPS-023، OPS-024) | ≤ دقيقة |
| **الكود** | إعادة `current` إلى مجلد الإصدار السابق (موجود على السيرفر: آخر 5). إن لم يوجد: إعادة نشر الـArtifact السابق المحفوظ (آخر 10) بنفس سكربت [`DEPLOYMENT`](DEPLOYMENT.md) §5 | ≤ 5 دقائق |
| **إعدادات `.env`** | نسخة `.env` السابقة تُحفظ قبل أي تعديل (`private_html/shared/.env.<release_id>`، صلاحية 600) وتُستعاد. `releases.config_changes` يذكر **أسماء** المفاتيح المتغيرة فقط | ≤ 5 دقائق |
| **إعدادات الـDashboard** (`settings` · `feature_flags`) | استعادة القيمة السابقة من `audit_logs` (قبل/بعد) أو `content_versions` | دقائق |
| **المحتوى** | استعادة نسخة من `content_versions` ← تمر بـPublish Guard ← نشر ← إبطال Cache بالوسوم ← `audit_logs` | دقائق، من الـOwner |
| **الـMigrations** | **لا تراجع لقاعدة البيانات في العادة:** المخطط متوافق للخلف بالتصميم (Expand → Migrate → Contract)، فالكود السابق يعمل على المخطط الجديد. `migrate:rollback` فقط لآخر دفعة، وفقط إذا كانت `down()` آمنة ولا تحذف بيانات | — |
| **الـCache** | مفاتيح Cache التطبيق تحمل `release_id` فتتبدل مع التراجع تلقائيًا. Cloudflare: إبطال **بالوسوم** للصفحات التي غيّرها الإصدار المتراجَع عنه فقط، لا Purge شامل ([`CACHE-CDN`](CACHE-CDN.md) §5) | دقائق |
| **التحويلات** | صفوف `redirects` بيانات: تُعطَّل (`ARCHIVED`) أو تُعاد قيمتها السابقة من `audit_logs` | دقائق |
| **الانتقال للدومين (Cutover)** | إعادة ربط الدومين بتطبيق WordPress القديم الذي **لم يُلمس** ([`LAUNCH-READINESS`](LAUNCH-READINESS.md) §4) | يُقاس في البروفة |

> **استعادة البيانات من نسخة احتياطية ليست Rollback.** هي Disaster Recovery، قد تُفقد بيانات أحدث من النسخة، وتحتاج قرارك ([`DISASTER-RECOVERY`](DISASTER-RECOVERY.md) §4).

## 2. متى نتراجع ومتى نصلح للأمام؟
| الحالة | الإجراء الأول | ثم | من يقرر |
|---|---|---|---|
| الموقع متوقف أو أخطاء 5xx واسعة بعد نشر | **تراجع فوري للكود** | تحقيق ثم إصلاح في إصدار جديد عبر نفس البوابة | تلقائي داخل نافذة التحقق (§3)، وبعدها **الـOwner** |
| النماذج لا تحفظ الطلبات | **تراجع فوري للكود** | حادثة HIGH | مثل السابق |
| خلل صلاحيات أو كشف بيانات | **Safe Mode/تعطيل الميزة + تراجع** | حادثة CRITICAL + مراجعة أمنية | الـOwner فورًا (زر)، بتوصية Claude |
| تجربة ديناميكية أو حملة مكسورة | Safe Mode أو إيقاف التجربة (Emergency Controls) | إصلاح | الـOwner (زر) |
| خطأ بصري صغير في صفحة واحدة | **إصلاح للأمام** | إصدار تصحيحي | Claude يقترح، والـOwner يوافق على الإصدار |
| تراجع أداء متوسط | **إصلاح للأمام** | — | مثل السابق |
| خطأ محتوى (سعر، ساعات، نص) | استعادة نسخة من `content_versions` | — | الـOwner من الـDashboard |
| Migration فشلت أثناء النشر | النشر يتوقف **قبل** التبديل؛ الإصدار الحالي يبقى | — | تلقائي |
| تحويل خاطئ بعد الإطلاق | تعديل أو تعطيل صف `redirects` | — | الـOwner يوافق على التعديل |
| فشل جوهري بعد الانتقال للدومين | إعادة الدومين إلى WordPress القديم | تحليل قبل محاولة جديدة | **الـOwner**، بتوصية Claude |
| بيانات تالفة أو مفقودة | ليس Rollback: **DR** (استعادة انتقائية) | — | **الـOwner** |

**القاعدة:** مشكلة P0 يراها العميل ← **تراجع أولًا، ثم التشخيص**. المشكلة الصغيرة المعزولة ← إصلاح للأمام عبر البوابة. **التراجع نفسه يُتحقق منه** (نفس فحوص ما بعد النشر).

## 3. من ينفذ التراجع؟ (الصلاحية من الخادم — M35 §58)
1. **تلقائيًا داخل نافذة التحقق بعد النشر:** إذا فشل التحقق، يعود السكربت إلى `previous_stable_release_id`. هذا **معتمد مسبقًا** لأن ملخص الموافقة على الإصدار يذكره صراحة ([`DEPLOYMENT`](DEPLOYMENT.md) §4).
2. **من الـOwner عبر الـDashboard:** **النظام ← الإصدارات ← [التراجع إلى الإصدار السابق]** + إعادة تأكيد الهوية. ينشئ طلبًا ينفذه المجدول (`release:rollback`) خلال دقيقة (صلاحيات الملفات وإعادة ضبط OPcache تُتحقق في الـAudit — [`DEPLOYMENT`](DEPLOYMENT.md) §5). **لا يحتاج GitHub ولا Terminal** (M35 §59).
3. **من Claude بطلب الـOwner** (الـDashboard أو رسالة صريحة).
- خارج هذه الحالات لا تراجع على Production بلا موافقتك (DEPLOY-001). عند حادثة CRITICAL يرسل Claude التوصية فورًا مع زر التنفيذ.

## 4. خطوات التراجع (`release:rollback`)
1. قفل يمنع نشرين أو تراجعين متزامنين.
2. التأكد أن الإصدار الهدف = آخر إصدار `LIVE` مستقر، وأن المخطط الحالي متوافق معه (من `releases.migrations`).
3. إعادة `current` (تبديل ذري) ← `optimize` ← `queue:restart` ← إعادة ضبط OPcache.
4. إبطال Cache بالوسوم المتأثرة ← تسخين الصفحات الأساسية.
5. تحقق بعد التراجع (نفس فحوص [`DEPLOYMENT`](DEPLOYMENT.md) §5 الخطوة 11).
6. الإصدار المتراجَع عنه = `ROLLED_BACK`، وسطر في `audit_logs` (من، متى، لماذا)، وإشارة في `signals` تُغلق بعد التحقق.

|---|---|
| تراجع الكود والإعدادات والمحتوى والتحويلات كما أعلاه | تراجع جزئي لميزة واحدة عبر أعلام أدق |
| زر التراجع في الـDashboard يُنفَّذ عبر المجدول | — |

## 6. البيانات
`releases` (`status`، `previous_stable_release_id`، `rolled_back_at`، `migrations`، `config_changes`) · `content_versions` · `settings` · `feature_flags` · `redirects` · `audit_logs` · `signals` · `scheduled_job_runs` (تشغيلات `release:rollback`).

## 7. مكانه في الـDashboard
- **النظام ← الإصدارات:** زر التراجع وسجل التراجعات.
- **زر ⚠️ وضع الأمان** في الشريط العلوي (OPS-023).
- **المحتوى:** "استعادة نسخة سابقة" داخل كل كيان.

## 8. اختبارات القبول
| # | الاختبار | المتوقع |
|---|---|---|
| RB-T1 | تراجع على Staging من إصدار N إلى N-1 مع طلبات GET متواصلة | ≤ 5 دقائق، صفر أخطاء 5xx |
| RB-T2 | إصدار N يحتوي Expand: تشغيل كود N-1 على المخطط الجديد | يعمل (اختبار CI إلزامي) |
| RB-T3 | فشل مقصود في تحقق ما بعد النشر على Staging | تراجع تلقائي، `ROLLED_BACK`، إشارة CRITICAL |
| RB-T4 | زر التراجع بلا إعادة تأكيد الهوية أو بلا جلسة Owner | مرفوض من الخادم |
| RB-T5 | استعادة نسخة محتوى سابقة لسعر منتج | السعر القديم يظهر في الموقع بعد إبطال الوسوم فقط، مع سطر Audit |
| RB-T6 | تراجعان متزامنان | الثاني يُرفض (قفل) |
| RB-T7 | بروفة إعادة الدومين للتطبيق القديم (على بيئة البروفة) | الزمن مقاس وموثق قبل الإطلاق |

## 9. ما لا يُفعل
- لا `migrate:rollback` يحذف بيانات، ولا Contract في نفس إصدار الـExpand.
- لا استعادة قاعدة بيانات كاملة كبديل عن تراجع الكود.
- لا Purge شامل لـCloudflare بعد التراجع.
- لا حذف لإصدارات أو Artifacts التراجع قبل أن يصبح الإصدار الجديد `LIVE` مستقرًا.
- لا وضع صيانة كامل إلا كآخر حل، وبموافقتك (AC-5).
